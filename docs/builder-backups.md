# Builder backups and recovery

L5-T5 supplies encrypted VPS backups, an independently encrypted workstation copy, recurring health observations and an isolated recovery drill. The schedules are enabled, and the L5 application/runtime rollout is live at `48823c6`. The external uptime workflow is on the default branch; paid Supabase PITR, an always-on offsite destination and actual notification delivery acceptance remain goal-end setup. Logical snapshots do not satisfy the launch plan's PITR requirement.

## Captured data

`scripts/ops/backup.py` captures explicitly configured sources using non-dereferencing rsync, encrypts them with restic, reads all encrypted repository data, and restores the snapshot privately. Every captured path, byte hash, permission, numeric owner/group and link target must match `manifest.json` before `last-backup.json` records success. A failed capture or verification preserves the previous receipt.

Working copies include original source, Git objects/refs, uncommitted changes, saved drafts, recovery and operation receipts. Dependencies and regenerable `.cache`, `.vite` and `.astro` directories are excluded. Links remain links and are never followed into unrelated files. Release stores include retained artifacts, manifests, immutable assets, transactions and the selected configuration. Operator configuration and project credentials are encrypted when explicitly included. Restic passwords stay outside the captured sources and must also be retained privately outside both backup machines.

The current 43 sources include hosted working copies; production, staging and client-demo release stores; Kaizen/helper settings; selected Nginx configuration; client-demo TLS/ACME state; and selected Kaizen DirectAdmin routing/TLS files, service units, sudo/reload configuration, account/runtime inventory and operations configuration/runtime. The L5 rollout adds the existing AppArmor profile and exact toolchain/helper/worker receipts; it does not alter the existing profile. A `file` source includes only the named file, excluding neighboring domains and configuration. The manifest maps each label to its original absolute path. New client stores and consequential server configuration must be added to the inventory when provisioned.

Helper locks include configured projects before cloning. Active builds, occupied or unresolved locks and active releases defer capture; no lock is stolen and no editor operation is cancelled. Release build flocks and activation locks are respected. A second checksum-based source comparison must find no changes before source locks are released. Direct changes during capture fail the attempt. Database/Storage capture happens before taking website locks. These are coordinated captures, not a single transaction across PostgreSQL, Storage, Git and release stores; recovery reconciles their selected state before workers resume.

Retention keeps seven daily, four weekly and three monthly calendar buckets, grouped by host and backup tag. An older recovery point can survive longer when there are no newer successful captures. Each repository retains its own recovery points independently; copying does not mirror source deletions. See [restic repository operations](https://restic.readthedocs.io/en/stable/045_working_with_repos.html).

## Database and Storage

`scripts/ops/supabase_backup.py` captures a full native PostgreSQL custom archive, role definitions without passwords, bucket settings and original Storage object bytes. The Management API issues a short-lived read-only login. Connections use the session pooler on port 5432, `verify-full`, and the provider CA. The export explicitly assumes `supabase_read_only_user` and proves a read-only transaction and `BYPASSRLS`. It never enables row filtering or excludes schemas to hide a failed export. A bounded authentication-readiness retry reuses the same password; a long capture renews an expired login before opening another connection.

The archive preserves schema, data, functions, triggers, RLS, ownership, grants and extension declarations. `pg_dumpall --roles-only --no-role-passwords` records role definitions/grants. Export failure or warning fails capture. `pg_restore` reads the archive catalogue and decodes every data block without connecting to a restore target. That validates the archive format; the separate native restore fixture proves the actual SQL restore on compatible PostgreSQL.

Storage downloads use the existing private worker service credential. Remote names are encoded as URL segments, while local files have hashed names. Captured metadata retains the original bucket/object identity, size and SHA-256. Supplied size, ETag and simple content hashes are checked. Partial/compressed responses, redirects, excessive bytes, duplicate identities or changed inventories fail capture. The Storage inventory must remain unchanged across the database export, excluding read-access timestamps. Database credentials, request headers and raw SQL error contents never enter operational output.

`data/supabase/capture.json` records PostgreSQL version, schemas, extension versions, bootstrap role, bucket settings and each object's source metadata and file/hash. A logical archive does not recreate provider infrastructure, externally configured secrets or provider encryption keys. Preserve a compatible Supabase recovery environment. Supabase's [database backups](https://supabase.com/docs/guides/platform/backups) exclude Storage object bytes; its [new-project restore](https://supabase.com/docs/guides/platform/clone-project) also requires separate service/configuration work.

## Installation and schedules

Examples are in `deploy/ops/backup.example.json`, `replica.example.json`, `monitor.example.json` and `restore.example.json`. Examples contain placeholders and are not a live-server inventory. Runtime modules are copied outside development checkouts into a reviewed immutable directory; `/opt/kaizen-ops` selects the VPS revision. The receiving operator uses `~/.local/share/kaizen-ops`. Keep configuration/state directories private and configuration/password files mode 0600. Run VPS backup/recovery as root when sources have several service owners; non-root recovery cannot prove restoration of their numeric ownership.

Initialize each repository explicitly once. A failed read must never initialize a new empty repository automatically:

```bash
python3 /opt/kaizen-ops/backup.py /etc/kaizen-ops/backup.json init
python3 /opt/kaizen-ops/backup.py /etc/kaizen-ops/backup.json capture
python3 ~/.local/share/kaizen-ops/replicate.py ~/.config/kaizen/backup-replica.json init
python3 ~/.local/share/kaizen-ops/replicate.py ~/.config/kaizen/backup-replica.json capture
```

The installed `kaizen-backup.timer` checks hourly. Its normal `scheduled` action captures when the verified receipt is at least 20 hours old, missing or invalid. A failed attempt retries on a later check. Exit 75 means a required operation lock was occupied; it is not a fresh backup. The system unit restricts writes to the private backup/state paths and the locks/stores needed for coordination. The receiving user timer checks hourly while the workstation is online. Service execution is bounded. A hard interruption can leave private partial data or an operation lock: inspect its process/owner and existing helper/release recovery rules before cleanup. Never remove an active lock to make a backup proceed.

`replicate.py` copies the exact last verified VPS snapshot using noninteractive SFTP and existing SSH host trust. It verifies source identity, destination original identity, manifest hash and all destination encrypted data before recording success. Destination encryption uses a different password. With `source.reportToSource: true`, the fixed SSH receiver acknowledges both snapshot identities and saves the receipt on the VPS. It rejects malformed, older or future-dated receipts. A failed acknowledgement preserves the actual verified local copy but fails the service so the next run retries. Repeated copies are idempotent.

The current replica is on Sean's workstation. It supplies an off-server copy while connected, not an always-on remote service. A separately retained replica password is sufficient for recovery; the original server, source repository/password and source configuration are not required.

## Monitoring and alerts

The enabled `kaizen-ops-monitor.timer` observes every two minutes. The 17 configured checks cover helper/Nginx/Apache/Exim and worker/timer states, helper HTTP health, selected production/staging/client-demo marker bytes, verified source and replica ages, disk reserve and aggregate recent hosted client/publication errors. Backup freshness has a 36-hour limit. The replica check uses its source capture timestamp: copying the same old snapshot cannot make the recovery point appear fresh.

Two consecutive failed observations queue one incident email through the existing Exim transport. Recovery queues one recovery email; unchanged incidents do not repeatedly queue messages. Queue failure is retried without marking notification success. Alerts contain check names and aggregate counts, not user identifiers, raw logs, page content or credentials. `check` is read-only and sends nothing; `run` updates counters and can queue real alerts:

```bash
python3 /opt/kaizen-ops/monitor.py /etc/kaizen-ops/monitor.json check
systemctl show kaizen-backup.service kaizen-ops-monitor.service -p ActiveState -p Result -p ExecMainStatus
systemctl --user show kaizen-backup-replica.service -p ActiveState -p Result -p ExecMainStatus
```

A successful inactive oneshot is healthy; a missing or failed unit is not. The query endpoint's successful HTTP 200/201 responses are accepted explicitly, while helper/website responses still require 200. The first installed monitor service run passed all 17 checks with `alertQueued: false`. Tests replace the mail transport. Exim queue acceptance is not proof of inbox delivery; actual delivery remains a final acceptance item.

`.github/workflows/kaizen-uptime.yml` independently checks the public Kaizen and client-demo HTTPS marker and homepage. It rejects redirects, missing/mismatched release identity and incorrect client destinations. Both real checks pass. The workflow is on the default branch after the L5 rollout; that alone does not prove a scheduled run or delivered notification. [GitHub schedules](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) can be delayed; [notification settings](https://docs.github.com/en/subscriptions-and-notifications/get-started/configuring-notifications) must route failures to Sean. This is complementary external monitoring, not a delivery guarantee.

## Recovery drill

1. Use synthetic temporary repositories/databases for rehearsal. For actual recovery, retain the damaged state and select an exact verified snapshot before changing routing. On a replacement host, copy the independent encrypted repository and its separate password into private, unserved storage. Install matching restic and reviewed operations code. For a multi-owner VPS snapshot, run recovery as root with root-owned private configuration/password files and a new mode-0700 state directory. Do not rely on passwords stored only on the lost VPS or workstation.
2. Create a mode-0600 recovery configuration from `deploy/ops/restore.example.json`, pointing to that repository, its password and the new state directory. It needs no original source paths, project credentials, database connection or original backup configuration. List snapshots with restic using its private password-file option and select the **replica** snapshot identity when restoring from the replica; its ID differs from the VPS source ID. Do not choose `latest` or paste backup contents into logs.
3. Restore into a **new, unserved directory**:

   ```bash
   python3 /opt/kaizen-ops/backup.py /private/recovery.json restore EXACT_SNAPSHOT_ID /private/new-recovery-directory
   ```

   Recovery reads the authenticated manifest before writing and rejects existing targets, repository overlap and every recorded original source path, including when those source directories are absent. It checks restored bytes, paths, modes, owners/groups and links against the manifest. The result identifies the verified capture root; its `data/` holds labeled sources and `manifest.json` maps their original locations. Recovery configuration cannot initialize or capture backups. Nothing activates automatically.
4. Recreate the account names, numeric ownership and runtime dependencies from the restored inventory. Omitted dependencies must be provisioned from the recorded reviewed revision and frozen lockfile. Restore operator configuration privately, preserving the separate release/helper service owners. Keep helpers, publication workers, restored cron and outbound email stopped during reconciliation. Inspect Git with `GIT_OPTIONAL_LOCKS=0` or as `kaizen-helper`; compare pending source, drafts and operation receipts. Use the existing interrupted-operation recovery procedure instead of clearing receipts or replaying pushes.
5. Restore the release store at its original path on the replacement host, or regenerate the Nginx include for the recovery location using the existing release engine. Saved includes contain absolute paths. A private listener must serve the **restored** artifact while the original store is unavailable. Verify its manifest, response identities, pages/assets, redirects and private-path denial. Activate a retained candidate and roll back through the same release engine. Confirm original unpublished edits remain unpublished. The fixture in `tests/ops/restore-site.mjs` and `test_website_restore.py` executes this drill with real Nginx.
6. Restore PostgreSQL into a compatible isolated target. For the native rehearsal, create the recorded bootstrap superuser and preserve PostgreSQL's empty built-in `public` schema. Prepare `roles.sql` by omitting only that bootstrap role's already-created `CREATE ROLE` statement; keep all its attributes/grants. Apply roles using `psql -X -v ON_ERROR_STOP=1`, then use `pg_restore --exit-on-error --single-transaction`. Stop the source server and verify both owners' rows, role grants, RLS, revision triggers and Storage metadata/hashes. `tests/ops/test_database_restore.py` performs these steps. On managed Supabase, use provider recovery and reconcile existing managed roles/extensions; do not blindly replay cluster roles into a live project. Provider-managed encryption keys and service settings need their own compatible recovery path.
7. Restore **object bytes separately** after database/provider recovery. Use `capture.json` to map each hashed `objects/<file>` back to its original bucket/name; verify its size/SHA-256 first. Follow the provider's [Storage migration procedure](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore#migrating-storage-objects) against the isolated recovery target, taking bytes from the verified local capture instead of downloading from a lost source. Restore bucket visibility, MIME/size constraints and original object paths. Use the Storage API to create/upload objects; do not assume SQL metadata restoration recreates their bytes. Reconcile ownership and access policies, verify downloaded bytes against every capture hash and verify authorized/unauthorized access before exposing the target. Object versions can change on upload; the restored manifest's original version is evidence, not a promise that the API recreates that version. A hosted Storage-upload rehearsal and managed-provider recovery acceptance remain external validation items; the native fixture proves recovered metadata and bytes, not a live hosted service restore.
8. Reconcile database publication heads with the exact verified retained artifact, project destinations and restored working copies. Reconfigure functions, Auth/redirect settings and required service credentials on a new provider project; retain private values outside logs. Record selected snapshot/artifact identities, verification and any manual repairs. Only an explicit recovery action may switch public routing and restart workers. Resume backups, replication and monitoring once the recovered state is verified; confirm fresh receipts and a healthy external response.
