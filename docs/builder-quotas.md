## Upload accounting

The ledger reserves space against the current website billing owner before an upload can begin. Each reservation binds the account, project, asset ID, kind, exact bytes, SHA-256, MIME type and worker. A retry must match that identity. Individual files are bounded at 50 MiB and a billing account can have at most 20 unfinished uploads. Account row locks serialize capacity checks across its projects.

Accounting reads existing Storage metadata, including unregistered and retained objects, and combines it with outstanding reservations. A reservation and its matching object count once at the larger observed size. Invalid or missing provider size metadata prevents a new reservation until usage can be verified. Project asset usage is the larger of the workspace declaration and physical/reserved usage; repository usage continues through the existing billing ledger. Removing workspace metadata alone cannot release retained object bytes. Billing transfers move the reservations and observed storage with the website; archive and downgrade preserve existing usage.

Cancellation requests cleanup without releasing capacity. Expiry alone cannot free space. Cleanup completion requires the worker's matching attempt, confirmation of local and provider removal, and observed absence of the Storage object. A completed upload cannot be deleted by cancelling its original import because saved work and history may still reference it. Separate reference-aware jobs now remove unused catalogued client files, as described below.

Stored completion requires a current upload owner with current confirmed-account and project access, fresh worker evidence, and matching provider size, version and ETag. The worker must verify actual file bytes and SHA-256 before issuing that evidence. Once completed, a lost-reply retry accepts only the identical saved receipt; changed identity, timestamps, fields or removal assertions are rejected. Private worker state is available only through service RPCs; browser responses omit worker identifiers, paths and ownership tokens.

## Hosted transfer decision

Use a controlled resumable upload service on the VPS, reusing the existing local TUS implementation and recovery primitives. It must reserve capacity before accepting bytes, enforce the declared stream length, verify actual size/hash, and write through the Storage API. The proposed browser and copy paths use this service. Migration 013 disables the old direct-write policies as part of the coordinated rollout; production still runs the previous transport and policies.

Supabase's uploader checks permission before transferring bytes and completes object metadata through a privileged database adapter. An RLS permission check alone therefore does not implement the required durable reservation and actual-byte enforcement. This decision follows the [Storage uploader implementation](https://github.com/supabase/storage/blob/master/src/storage/uploader.ts). The migration reads Storage metadata without changing provider-owned tables or schema; object writes and removals must use the API, as required by [Storage schema guidance](https://supabase.com/docs/guides/storage/schema/design).

Worker takeover must prove the previous process stopped and acquire the local operation lock before changing the database owner. The database compare-and-swap prevents old callbacks from completing; it does not establish that a remote process stopped. Both interactive requests and automatic cleanup use these checks with the temporary spool and provider adapter.

## Temporary upload storage

`UploadSpool` reuses the hosted folder privacy checks, existing process-lock recovery and TUS FileStore interface. Default operational limits reserve at most 2 GiB of temporary files, 1,024 unfinished transfers, and 2 GiB of free filesystem headroom. These are additional VPS limits; the database enforces each billing plan. Each reservation also charges 64 KiB for recovery metadata. Operator configuration can lower or raise these bounds within the validated limits.

The durable local reservation is the sole authority for TUS size and metadata; the actual file length supplies its resume offset. Exclusive file creation prevents a repeated POST from truncating an existing transfer. Writes require the operation lock, the current offset and a fixed reservation, and cannot exceed that reservation even if a caller bypasses TUS header checks. Completion measures actual bytes and SHA-256. Source stream errors preserve a bounded partial file for resume. Symlinks, hardlinks and non-private state are refused.

Cancellation cleanup removes the local file before releasing its reservation. Recovery metadata remains charged until the service has acknowledged terminal database completion and explicitly forgets it. The service must not call this final cleanup while a provider or database outcome is unknown. Different local workers cannot replace a live or foreign-host process; replacement needs a proven stopped process. An existing token cannot change its recorded process identity.

The HTTP integration produces its TUS response under the operation lock and sends that response after the lock is released. The real HTTP fixture exercises `handleWeb` this way, preventing a client's next PATCH from racing the preceding response's lock cleanup. `HostedUploads.handle` returns a Response for `scripts/builder-upload-host.ts` to send after cleanup.

## Authenticated transfer and provider completion

`HostedUploads` verifies each caller through the existing hosted Auth adapter, then rechecks current upload ownership and project/account access through service-only RPCs. POST reserves the database allowance before creating local storage. The upload ID is stable for its immutable project and asset, so a lost creation reply can be retried without creating another reservation or truncating bytes. Transfer size and metadata are fixed; unsupported protocol versions, creation bodies and malformed routes are refused. HEAD and PATCH use the existing TUS implementation. At most four requests are active per service instance.

Completion verifies local bytes, checks current access, transfers through the private provider adapter, and rechecks access before submitting its receipt. The adapter validates bucket/key ownership, uses HTTPS without redirects, streams a bounded download to verify SHA-256, and compares the exact size/version/ETag before and after reading. Writes disable overwrite. If a write succeeds but its reply is lost, a retry verifies the existing object instead of writing another one. Unexpected bytes remain untouched.

Cancellation targets the observed provider version, verifies that the object is absent, removes local bytes, and persists its receipt before releasing the database reservation. A missing bucket or arbitrary HTTP 404 is not accepted as object-removal proof. The chosen single-object deletion route supports an explicit version, and the provider implementation awaits backend deletion within its database transaction; see [the delete route](https://github.com/supabase/storage/blob/master/src/http/routes/object/deleteObject.ts) and [the Storage object implementation](https://github.com/supabase/storage/blob/master/src/storage/object.ts). Actual compatibility and cleanup on the configured hosted provider remain rollout checks.

Prior local attempt records are retained when a worker takes over. If a new process stops after recording its intent but before claiming SQL ownership, recovery can still identify the database's earlier owner and prove that process stopped. History is bounded at 64 prior attempts and by the state-file size allowance. Terminal database readback precedes local metadata removal. Unknown write/completion outcomes preserve data and charges; cleanup can retry after local bytes are gone but SQL completion has not yet succeeded.

## Automatic unfinished-upload cleanup

The service checks a bounded queue every minute, without overlapping passes. Successful new bytes refresh a seven-day resume window; HEAD, repeated creation and empty or failed PATCH requests do not. Explicit cancellation, expiry, archive, loss of membership, unconfirmed/deleted accounts and an account deletion in progress make unfinished uploads eligible. A background pass acquires the same local operation lock as foreground uploads, then rechecks current eligibility before requesting cancellation. A resumed upload can invalidate an earlier queue result. The combined foreground/background service limit remains four operations.

Cancellation still retains the full billing reservation. The worker verifies provider removal, removes local bytes, records its durable receipt and obtains terminal SQL confirmation before freeing capacity. A lost POST that never created a local file can be cleaned using only a small recovery record; cleanup does not need to reserve the missing file's entire size again. Unavailable provider/database outcomes remain charged and retryable. Failed items rotate behind other eligible work. Shutdown lets the active cleanup operation finish and prevents another batch from starting.

Terminal rows stay discoverable until the service acknowledges removal of local bytes and recovery state. A lost acknowledgement is reconciled on a later pass, including after restart. The transfer queue preserves stored provider assets. The worker also runs the separate stored-file queue below, with reference checks and its own durable removal identity.

## Verified library registration and existing-file recovery

Migration 012 adds a private catalogue of file identities. An entry binds its project and asset ID to exact size, hash, MIME type, kind and provider key. Existing registered assets are backfilled as **legacy** identities, preserving their addresses without claiming a fresh verification of their bytes. New uploads populate a **verified** identity atomically with their stored completion receipt. A missing provider file cannot make its existing library identity available for a different upload; replacements use a new asset ID.

Both original Kaizen and client projects register files through the existing projects function. Its service RPC checks the verified identity and current provider size/version/ETag before writing the library entry. Canonical addresses come from trusted configuration and project identity. Direct client inserts into the original asset table are revoked; metadata edits and workspace saves must preserve file identity and address. A retry returns an already registered matching entry without overwriting later metadata.

Recovering an existing provider file calls `/editor-uploads/adopt`. The service verifies its actual bounded bytes/hash and unchanged provider metadata, rechecks current account access and registers fresh evidence. Adoption creates no extra transfer reservation, grants no removal authority over that existing file and can recover already-counted bytes after a downgrade. Incorrect bytes or access loss leave the existing file intact. If an ordinary upload wrote the file but lost its database completion, adoption reconciles that original upload under its ownership and process checks before making it available to the library.

## Native reference inventory

`scripts/builder-native-asset-references.ts` reuses the source-accounting reader through an optional streaming observer. It matches asset IDs and literal, JSON-escaped, HTML-escaped and URL-encoded addresses without returning file contents or private paths. Per-file decoders retain split UTF-8 sequences and identifiers, without joining separate files. Source accounting retains its existing generated/dependency exclusions; the hosted inventory separately covers saved account drafts, source/build recovery, retained builder state and current output, plus explicitly configured retained release stores.

Git history uses the local [Git batch object reader](https://git-scm.com/docs/git-cat-file), including packed and unreachable retained objects. Every object is hashed against its actual Git identity. Retained tree filenames identify compressed archives, including Brotli; ZIP/gzip signatures also identify unreachable archives with no remaining filename. A second bounded read decodes selected archive objects, so their ordering in Git cannot hide a filename encountered later. No checkout, fetch, filter, hook or archive extraction is performed. Alternate object stores, linked metadata, nested repositories, in-progress Git lock files and corrupt objects make the inventory incomplete.

ZIP, gzip and Brotli files are decoded in memory with a 35 MiB compressed-input limit, 200 MiB expansion limit per archive, bounded entries and three nesting levels. Overall file, object and byte limits bound the scan. Source, file inventories and Git metadata are rechecked for changes. An unreadable file, failed process, exceeded bound or cancelled check never becomes an empty reference result. The hosted entry point verifies the configured repository/branch and runs under the helper's ordinary project lock, refusing an active build.

**Integration boundary:** this is a read-only snapshot, not permission to delete native assets. Cleanup must keep producer operations serialized while it checks all configured source/recovery/release locations and claims removal. Future helper edits, builds, publication and recovery must reject references to a removing/removed file. Original Kaizen assets can also be referenced by other native websites, so checking only its helper checkout is insufficient. Operator-configured native client projects need the same protection before the upload timer is activated. The durable coordinator, producer guards and their contention proof remain required; the current original-Kaizen deletion refusal stays in place.

## Native operation and cleanup coordination

Migration 017 records the complete operator-configured native project inventory, its configuration fingerprint and allowed producer workers. Protected project scopes are retained across reconfiguration. This includes native client projects, which are removed from the ordinary upload worker's cleanup queue. Existing pending jobs transfer to the native cleanup worker and regain the recovery window. Configuration changes cannot discard retained scopes or overtake an active producer or native removal. Cleanup is disabled by default; enabling it is part of the final coordinated installation, after the callers below are implemented and verified.

A producer records its immutable request, project, worker, configuration, process, host and process-instance identity before changing files. Active operations have no expiry that permits cleanup. Both beginning and completing an operation advance a database generation. A root scanner first observes that generation with no active producers, scans every applicable configured source/draft/recovery/release root, and then records a clearance bound to the cleanup job, exact attempt token, configuration and inventory fingerprint. The claim rechecks the generation and active operations. An edit which begins and finishes entirely between scan and claim still invalidates that scan.

After removal is claimed, later producers retrieve the removing/removed file identities for their project and original Kaizen files in bounded pages. The private `NativeFileProtection` checks prospective bytes against IDs and historical URL spellings, including compressed content. It rejects a retired reference before a caller writes those bytes. The database reference guards continue to protect saved content and history. Neither the list of retired addresses nor local file contents are returned to the browser.

`NativeOperationJournal` persists a private, synced intent before asking SQL to begin. It awaits the entire work promise, persists a finished record, and only then asks SQL to end protection. A lost begin can be reconciled by end; an end that arrives first creates a tombstone, so a delayed begin cannot reopen the operation. A failed end retains the local record and database protection. Finished records can be retried without the user's expired Auth. Recovering an unfinished intent requires the actual host controller to prove that all work, including child processes, stopped. The default makes no such assumption; a timestamp or dead parent PID alone cannot release protection.

The existing `builder-billing` endpoint carries these narrow helper operations using its existing HMAC signature. Begin and retired-file reads require current verified Auth. End requires the signature and exact durable operation identity, and remains usable after Auth expires. Global request limits still apply. Browsers have no access to the new private tables or worker RPCs, and the helper receives no database service-role credential.

Register all operator-configured native clients and retained checkouts before enabling either cleanup timer. ## Hosted helper and build integration

When its operator-only native configuration is supplied, the helper starts a journal operation before entering the website-folder action and finishes it after that action settles. This covers setup/connection, source editing, drafts, Git operations, save/publication requests and the existing receipt recovery inside those requests. Draft and repository-setting payloads are checked before writing. `RepositoryCompanion.apply` supplies actual replacement bytes to its private before-mutation callback, alongside its existing hashes and usage measurement, so the helper can reject a newly retired reference even if it was still available when the change was reviewed.

Asynchronous builds have their own operation which spans startup, the actual runner, output checks and recovery. Every rendered file is checked before the runner opens a preview. The queue reports completion only after the native end is confirmed.
