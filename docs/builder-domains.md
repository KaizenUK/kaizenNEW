## Hosting decision

Use the VPS's existing DirectAdmin/Apache installation for public HTTP, HTTPS and certificate renewal, with the existing Nginx release stores behind it. This keeps domain publication on the release engine already used by Kaizen and client websites.

DirectAdmin supports account domain creation through its [domain API](https://docs.directadmin.com/developer/api/legacy-api.html) and domain-specific Apache changes through [Custom Httpd Config](https://docs.directadmin.com/webservices/apache/customizing.html). Its [current API documentation](https://docs.directadmin.com/developer/api/) identifies the installed server's `/static/swagger.json` as the API reference. Read-only inspection of Kaizen's installed schema on 15 September confirmed the domain ACME configuration, certificate provision/dry-run and certificate inventory endpoints. This establishes which integration to build; no domain or certificate was created by that inspection.

The worker must verify the exact hostname, certificate validity and automatic renewal, then verify a served release before making a destination available. Provider success responses alone are insufficient. DirectAdmin may include other names in certificate requests, so provisioning must restrict and check the requested names; verifying one domain must not implicitly connect `www`, mail or wildcard names.

## DNS checks implemented

`shared/builderDomains.ts` gives the browser and server the same normalized ASCII hostname, including international domain names and a single final DNS root dot. It rejects links, paths, credentials, ports, IP addresses, wildcards, malformed labels and private/reserved suffixes. The ownership record's full DNS name must fit the DNS length limit. Operator reservations protect existing service names and their subdomains.

The server generates a fresh 256-bit random challenge for each domain claim. The owner adds a TXT record named `_kaizen-verification.<hostname>` whose complete value starts with `kaizen-domain-verification=`. Fragments within one TXT record are joined; fragments in separate records do not prove ownership. The database persists the challenge for that claim and replaces it when a removed domain is claimed again.

`scripts/builder-domain-dns.ts` checks ownership before resolving the website's A and AAAA records. At least one address is required, and every returned address must match the worker's fixed hosting configuration. An old or foreign AAAA record prevents connection even when the A record is correct. Equivalent IPv6 representations compare consistently. DNS timeout or refusal is a failed check, not evidence that the record is absent. Checks are fresh on each call and do not fetch URLs from DNS answers.

The result distinguishes missing ownership, missing routing, conflicting routing and failed lookups. It contains no raw TXT records or internal resolver errors. Addresses are checked against operator configuration; website requests cannot choose the trusted addresses.

## Domain claims and release bindings implemented

The existing projects endpoint now handles `domain-state`, `domain-add`, `domain-verify` and `domain-remove`. It verifies current membership before dispatch. Changes require an owner with publishing permission, an observed domain version and explicit removal confirmation. The server generates the challenge and selects the configured worker; a request cannot supply an actor, verification result, provider receipt or hosting route. Missing hosting configuration leaves status readable and prevents new claims.

`BUILDER_DOMAIN_CONFIG` is server configuration containing `workerId`, `ipv4`, `ipv6` and `reservedHostnames`. Only the IPv4/IPv6 instructions accompany public domain status. For newly provisioned client destinations, the configured worker ID must also identify the client publication worker on that host. This configuration still needs to be installed with the coordinated L6 rollout.

Migration `202609150009_builder_domains.sql` adds a private domain table and service-only routines. One current domain is allowed per website. Different projects may initially request the same hostname, so an unverified request cannot reserve somebody else's domain. Verified ownership becomes exclusive before provider setup. Removed claims remain in history, and adding the hostname again creates a fresh identity and challenge.

A new self-serve website receives a new primary destination only after a verified empty release baseline and certificate are ready; publishing drafts remains a separate action. For a website with an existing manually configured production address, the domain is an additional address for that existing release store. It does not change the store's original origin or canonical content. The original repository site's alias similarly binds to the current production artifact. No old manifest or destination identity is rewritten.

The worker's completion receipt must bind the domain, project, attempt, hostname, destination and current artifact. The database requires fresh DNS and TLS evidence, the exact certificate hostname, automatic renewal, a non-self-signed certificate with remaining validity, and hashes of the certificate and served release. An alias must match the current production artifact. A new primary destination must use its own empty baseline. These are receipt checks; the hosting worker must still perform the actual network and provider verification.

Removal disables a primary destination and retains its files, jobs and drafts. Removing an alias leaves the original destination enabled. Reconnection provisions a new destination; disabled historical destinations may retain the same origin. Retired jobs remain in release history and no longer appear as current. Domain changes and new publications are serialized through the project's database lock, with pending publication/recovery blocking domain changes.

An interrupted worker requires an explicit previous-owner comparison and replacement token. Elapsed time alone does not authorize takeover; the host must first hold its filesystem lock and prove the previous process stopped. Late callbacks are refused. An already-authorized removal may finish after its requester loses access, because cleanup cannot reconnect, reassign or delete the website's data.

## HTTPS and local provider transport implemented

## Exact-name certificates and host preparation

[`builder-domain-certificates.ts`](../scripts/builder-domain-certificates.ts) disables default ACME settings, inspects a disabled dry run and excludes every other pending, failed, skipped or obsolete DNS name before enabling issuance. This includes mail, `www` and wildcard names that could otherwise become issuable after a later DNS change. Only the requested hostname and HTTP-01 challenge may remain. It reads back settings after changes, handles ongoing/rate-limited/lost requests as pending, and reconciles a successful issuance whose response was lost without submitting another request.

The certificate inventory must report a valid, non-self-signed certificate for the exact name with automatic renewal enabled. `verifyDomainHttps` now also returns the served certificate's serial number. The worker must compare serial number, exact names and expiry with the provider evidence using `assertDomainCertificateMatches`, in addition to the existing chain, hostname, leaf-hash and served-release checks. Renewal metadata for a different certificate cannot confirm the one being served. Provider output and DNS-provider environment values are never included in errors.

The provider's `withOwned` operation holds the ownership lock, verifies the journal/custom configuration and rechecks the caller's guard throughout certificate setup. Its API wrapper permits only this domain's certificate routes and the fixed SSL-enabling body. It rejects other hostnames, traversal and domain deletion disguised as modification.

The existing `admin_ssl_install_to_missing` and `admin_ssl_replace_all_expired_invalid` settings remain **0**. The root API factory checks all three before creating a domain; these broad creation/repair triggers must not race the builder's exact-name plan. This changes automatic initial certificate creation for future manually added domains too: those domains need explicit ACME setup. Existing renewal settings and the production release were preserved. DirectAdmin documents these [automatic certificate triggers and the distinction from existing retries](https://docs.directadmin.com/webservices/ssl/automatic-ssl-certificates.html).

The modern domain certificate API still defaults to `enabled: true` when the legacy creation trigger is off. The owned-object adapter therefore explicitly saves and reads back disabled ACME configuration during initial setup, before confirming its route. A read-only dry run of the existing Kaizen domain first confirmed that disabled planning works and can include additional names; it did not change that domain's settings or request a certificate.
