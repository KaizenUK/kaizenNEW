# Local client projects and repository handoff

The hosted builder is live at https://kaizenweb.co.uk/builder/. Invited users choose a password using their invitation link, then sign in with email and password. Open registration is disabled. Sean's account has owner/publish access to the original Kaizen workspace. The live invitation/password/project-reopen flow and hosted access isolation have passed acceptance; see [progress and verification](builder-project-progress.md).

For filesystem/repository integration, run `pnpm dev` on your workstation. You can use the local `/builder/` directly or connect the hosted editor to its companion window as described below. The client publication worker is installed and supervised on production. **Client demo acceptance** publishes to https://client-demo.kaizenweb.co.uk on the approved VPS; Sean is its sole owner/publisher. Each additional client needs its own explicit destination before publishing.

## First client project

1. Open **All projects**, enter a name and choose **Create project**, then **Open project**. The active name and destination appear in both the sidebar and editor.
2. Import images, fonts and reference files through **Assets**. In **Settings**, set the public HTTPS site origin, choose a favicon, configure an optional public form receiver and choose an explicit CMS connection. Create pages, edit shared design, save and preview. Client pages can use `/about/` and `/contact/`; technical routes remain reserved. Each project has separate pages, assets, saved sections/templates, shared styles, client settings, history, uploads and private previews.
3. Use **Export & handoff → Download website ZIP**. Read `HANDOFF.md` for commands, missing internal links, media and external services. The output is a React/Vite static website. Run `pnpm install`, `pnpm build` and `pnpm preview` in the extracted folder. Deploy only `dist/` to the intended client host.
4. Keep `.kaizen/project.zip`: it is a separate editable backup inside the website ZIP. The website's resolved `src/pages.json` is generated output; the backup retains visual structure, original assets, shared definitions and revision history. **Project backups** also downloads this editable backup independently. Do not publish `.kaizen/`, reference packs, source or history as public files.

Creating or duplicating a project leaves its deployment destination unconfigured. Reopening a project retains its configured destination. To publish from Unity, first provision an explicit client destination using the [publication setup guide](client-publication.md). Open **Releases**, choose the staging or production destination, review the saved project and start publication. The editor's **Publish** action saves and opens this review; saving or exporting alone does not publish. Success requires checking the served output. Releases also provides history, reviewed rollback, unpublishing and recovery without replacing newer drafts. A new client never defaults to Kaizen's site. The [client demo operations record](client-demo-operations.md) records verified production publishing, rollback, unpublishing, failed-release restoration and draft retention. Process-crash recovery has isolated real-Nginx evidence; a deliberate crash on the public host is not required by the original acceptance request. Client service configuration remains deferred.

The original workspace is registered as **Kaizen workspace** in its existing directory. Registration does not move or rewrite its drafts, publications, assets, uploads, previews, submissions or history. `projects.json` is the catalogue; new project stores are under `.kaizen-builder/projects/<id>/`. Duplicates copy registered assets and all workspace history, remapping local asset references. They reset the site URL, form receiver and CMS connection, and do not copy submission records, private preview links or destination configuration. Choose the new client's services explicitly. Archive is reversible and prevents writes.

## Integrating a cloned repository

### Connect the hosted editor to this computer

1. Run `pnpm dev` in the updated Kaizen checkout. In the hosted builder, open a client project and **Export & handoff**.
2. Enter the local address printed by the development server (normally `http://127.0.0.1:4321`) and choose **Connect helper**. Allow the new companion window if the browser blocks it. Keep the terminal running; Ctrl+C stops the server. The command binds explicitly to IPv4 loopback and refuses an occupied port instead of silently choosing a different one. For another port, run `pnpm dev --port 4325` and enter that address in the hosted builder.
3. In that local window, check the requesting origin, account and project, choose the absolute repository folder and **Allow this folder**. Keep the window and local development server running. Editing controls remain in the hosted tab.
4. Return to **Pages → Pages from the website's code → Edit**. Review the first **Build** command, then edit the rendered page, review and apply its changes. The canvas rebuilds after application. Optionally **Commit these changes**; pushing remains a separate GitHub Desktop action. The older source editor and separate selection window under Export & handoff remain fallbacks.

The companion grants one tab access to one approved folder for two hours. Only `https://kaizenweb.co.uk` is approved in normal operation. Exact window/origin/channel checks protect browser messages; local HTTP retains its same-origin, loopback and Host checks. The opaque server capability remains in the local window, and the cloud token stays in the hosted window. Review and build IDs belong to the connection that created them. Cloud membership continues to protect cloud workspaces; access to this computer is granted by the local approval window.

Use **Stop sharing this folder** or close the companion to end the connection. Closing the hosted tab sends a best-effort revocation. The helper checks the parent window and its local server session; stopping or restarting the server triggers the editor's reconnect banner even if the approval window stays open. The server enforces the two-hour expiry independently. Website builds do not reload the approval window or renew its expiry. Already accepted operations can finish. After interruption or a timeout, inspect their result before retrying writes. Reconnect to the same folder to keep the source editor's open state; review again because old review/build IDs are not transferred to the new connection. To choose a different folder, open a separate hosted builder tab.

Local source drafts are stored under a dedicated local project for the hosted origin/account/project, then separated by repository and route. This mapping survives server restarts and cannot alias the original Kaizen workspace or another hosted account. Cloud builder pages and assets remain in their cloud workspace; this connection does not automatically synchronize whole cloud/local workspaces. **Open in local builder** reopens a compatible repository's builder backup as a separate local project.

For native restoration from the hosted editor, open a separate hosted tab, connect to the intended **new** folder and check **New folder for restoring a native backup** in the companion window. Its parent must exist and the target must not. The restore panel uses exactly this approved folder. Then upload the native ZIP and review/apply restoration. Keep environment credentials separately.

### Inspect and integrate

GitHub Desktop can keep managing the repository. No GitHub API connection is needed.

1. Choose **Export & handoff**, enter the absolute folder path and **Check folder**. The local development server performs filesystem operations; a hosted browser cannot freely access these folders.
2. Supported targets are Astro with `@astrojs/react`, the documented Kaizen export format, and an empty repository. Astro targets also need `htmlparser2` for the reviewed rich-text renderer; the companion explains a missing dependency before writing. Inspection never installs dependencies or runs repository scripts.
3. The route inventory marks builder-owned files as **builder-editable**. Ordinary existing routes remain **code-managed**; dynamic routes and source needing adaptation are labelled **developer-integration**. This is not an arbitrary Astro/React source importer.
4. Choose **Prepare file proposal**. Review file paths, create/update/delete actions and expandable proposed text. A conflicting file or existing route blocks applying. Changes made after review invalidate the proposal.
5. **Apply changes to the folder** writes the changes. Astro receives renderer modules in `src/kaizen/` and individual generated `.astro` routes. Existing package/configuration files, unrelated routes and components are preserved. A root page is generated only when an `index.astro` is absent or already builder-owned. Existing dynamic route ownership requires developer integration.
6. Review the uncommitted changes in GitHub Desktop. Install dependencies in the destination folder, then choose **Check build command → Run build**. The command and package lifecycle scripts are shown before running. Open the resulting **local website preview** to check the built site. Committing, pushing and deployment are separate actions. The optional **Commit these changes** step records only the last applied files. The companion performs no resets, pulls or pushes.

Browser integration currently accepts exports up to 35 MB (base64 is carried in the local API request); the underlying ZIP reader limits compressed archives to 50 MB and expanded data to 500 MB. Download larger exports for a developer handoff. File previews are bounded to 100 KB per text file. Proposals expire after 15 minutes.

## Edit pages created outside the builder

Open **Pages → Pages from the website's code → Edit** after connecting the helper. In the local builder, the running checkout is available without pairing. The existing-page inventory opens this same canvas. The older source-only editor remains available under **Export & handoff** as a fallback.

The content editor reads original `.astro`, `.tsx` and `.jsx` files and follows relative component/content imports and the `@/` client alias. Imported `.ts`, `.js`, `.mjs` and `.json` files and barrel re-exports expose supported literal content properties; named literal variables such as `headline`, `title` or `copy` are also editable. A `.js` import can resolve a matching TypeScript source when no JavaScript file exists. Imports stay within `src/` and `client/`; package imports and other aliases are not followed. Imported shared files can include fields unused by the selected page, so review their file and field labels.

The editor exposes literal text and quoted links/images. Astro sections can be moved within their existing container. Imports, CSS, scripts, event handlers, hydration directives and computed expressions remain in the original files. Shared component or data-file changes affect every page importing that file; CMS/computed data still needs its existing data source. Data files participate in the same version checks, reviewed proposals and recovery copies. JSON replacements must remain valid JSON. This is source-preserving content editing, not conversion of arbitrary code into Puck blocks or support for arbitrary layout changes.

Choose **Review my changes**, check the files that will change, then **Apply changes to the folder**. Changing content after review discards the displayed proposal. Applying checks the original source and imported files again, retains originals in `.kaizen/recovery/<proposal-id>/`, and leaves changes uncommitted for GitHub Desktop. The page editor rebuilds its preview after apply using the reviewed command. Use **Commit these changes** if you want to record those files in Git. Native source remains the source of truth; these changes are not included in a builder project's editable ZIP.

Unapplied content and section-order edits now save automatically in the selected project's private local `source-drafts/` directory, separately for each repository and route. Wait for **Editing draft saved on this computer** before leaving. Closing and reopening or reloading restores them; successful application clears only the matching saved draft. Another window's newer edits are never silently replaced. If original source files change, the editor retains the old draft for recovery and requires discarding it before a new proposal. Use **Download unapplied source edits** to retain a separate JSON recovery copy; this is not an importable builder ZIP. Draft read/save errors remain visible with retry controls. Local source drafts are not copied by dashboard project duplication; use the native repository backup below to copy the source and its saved drafts together.

The page editor embeds the real snapshot and edits matched words directly; see [the on-page journey](#on-page-editing-september-2026-implementation). Its window-preview fallback retains the older source-selection toolbar for browsers that cannot embed the helper. Both views require a build matching the current source and keep forms and API requests disabled. Only the connected editor origin may embed a canvas snapshot; ordinary window previews remain unframeable. Stopping or expiring the preview removes its snapshot.

Filesystem operations run through the local companion, either from the local editor or the paired hosted editor. The isolated native-site scenario checks source preservation, section order, build, desktop/mobile rendering, image loading, navigation and a hydrated counter after editing. A separate cross-origin scenario exercises the actual hosted repository UI, consent popup, real local APIs, saved-draft recovery, reviewed file application, builds, rendered selection, disconnect/reconnect and native backup restoration. Only its cloud identity/catalogue is simulated; production acceptance is recorded separately in the progress document.

## Native repository backup and reopening

After inspection, the last repository folder is remembered in this browser separately for each selected project. Reopen **Export & handoff** and inspect that folder again to refresh the source inventory. Browser preference storage can be unavailable; source files and saved editing drafts still live on disk through the companion.

For an existing Astro + React site, close its source editor after saving, then use **Review native repository backup → Download reviewed native backup**. The review lists the captured source/assets, exclusions, saved draft routes and discovered environment variable names. The ZIP contains `repository/`, a versioned/checksummed `native-project.json`, and `RESTORE.md`. It preserves native files and that selected project's unapplied source drafts separately from the builder page-data backup format. Drafts for pages that have since disappeared remain recovery data in the manifest.

To restore, select the destination client project, choose the ZIP under **Native repository backup ZIP**, enter an absolute **New restore folder** beneath an existing parent, then **Review native repository restore → Restore reviewed native repository**. The target must not already exist. Review and execution both check it; files are created without overwriting existing files and their bytes are verified. Restore keeps source file modes where supported and creates private source directories. A failed partial restore retains its files and reports their location; keep the original ZIP and choose a fresh target for retry. No original repository is removed or replaced.

Restoration rebinds saved editing drafts to the new folder and selected project. Inspect the restored repository, open an existing page, then review and apply its restored pending edits. The original repository and other projects' drafts remain unchanged. Install dependencies, review/run the restored repository's build and inspect the real preview before deployment. GitHub Desktop can subsequently manage the restored source; no Git or build commands run during backup/restore.

Limits are 35 MB compressed ZIP, 200 MB expanded data, 10,000 source files and 32 MB per file. Symlinks and unsafe/non-portable paths are rejected. Git history, dependency/build/cache folders, local builder stores, old companion recovery folders, most hidden files and known credential/key filenames are excluded. The review and `RESTORE.md` list the exact exclusions. Only variable names are retained from local `.env` files; configure values and any excluded tooling/registry settings separately. Four frozen reviews are retained for up to 15 minutes; newer reviews can expire the oldest unused one. This is a source backup, not a server/system image or a deployment artifact; deploy the separately verified build output.

## Local builds and previews

Build commands execute with your local user's permissions and terminal environment, like running the command yourself. Review unfamiliar repository code first. The runner invokes the companion's available pnpm/npm CLI with `run build`; dependencies must already be installed. It does not install packages, run Git commands or publish. The reviewed build may run lifecycle hooks and imported code. This is not a sandbox for untrusted scripts; builds that launch detached services require developer supervision.

Reviews expire after 15 minutes. Source checksums reject changes between review and execution or during the build. Source scanning excludes dependency directories, Git metadata, dist, common build caches and build recovery copies; it supports 10,000 entries and 200 MB. Keep generated files in the build output/cache directories. Linked source directories and linked output folders require developer integration.

The companion builds into a fresh `dist/`: it moves existing output to `.kaizen/build-recovery/<job-id>/previous-dist` first. On failure or cancellation it retains partial output as `failed-dist` and restores the previous output. It reports recovery failures and leaves the originals for manual recovery. Successful builds also retain the previous output. Review or remove these recovery folders yourself when no longer needed; they are local recovery data, not public files or editable source. Builds time out after five minutes. At most two builds can run, with one per repository. The UI can cancel a build and retains its job reference when you reopen the repository in the same tab. Jobs and previews end when the companion stops.

Only static output in `dist/` with an `index.html` is supported. The runner freezes the built files, serves them on a random loopback port, then checks that the served homepage matches the build before reporting success. Preview access requires the random link and a private cookie. Root-relative navigation works; hidden/source metadata and source maps are excluded. Forms and network API calls are disabled in this preview. Test deployed services separately. Files are limited to 32 MB each, 200 MB total and 10,000 files/directories. Previews expire after one hour; at most two are retained, so a third replaces the oldest. Eight recent jobs/logs are retained in the companion process. A local preview does not implement host redirects, server routes or deployment verification.

## Reopening and conflicts

Inspect a compatible repository and choose **Reopen as a separate editable project**. The companion verifies the recorded generated-file checksums and editable assets, then creates a separate local project. Existing local drafts are preserved. Make another visual edit, save it and prepare a new proposal for the same repository.

`.kaizen/format.json` identifies repository format version 1 or 2; `.kaizen/project.zip` uses editable backup version 2 when client settings are present, otherwise version 1. This builder reads both versions; older builders reject version 2 instead of discarding settings. `.kaizen/ownership.json` retains its version-1 generated-file checksums. Unknown versions stop the operation. External modifications to generated files, including deleted files, require reconciliation before reintegration/reopening. They cannot automatically become visual editor changes. Keep developer-owned additions in separate files or deliberately adapt them through the component registration contract in [component integration](builder-component-integration.md).

Before applying updates the companion retains original files under `.kaizen/recovery/<proposal-id>/`. If application fails, it reverts files still matching that operation's output and identifies files needing manual recovery. Concurrent developer edits are preserved. Review the working tree and recovery copy after any filesystem failure.

## Current delivery boundaries

- CMS content in a website export is a snapshot. **Settings** supports an explicit public Sanity project/dataset using the existing post/category/author schema and fixed published-only query. **Test saved CMS connection** reads the saved configuration. New projects never inherit Kaizen's CMS or server token. Private datasets and other schemas need a server integration; exported sites make no live CMS calls. Article links outside the exported page set appear in handoff warnings.
- Forms export with the receiver configured in **Settings**, or disabled if empty. The receiver must implement the contract in `CONTACT-FORMS.md`, accept the site's origin and handle notification delivery separately. Client editor previews cannot submit into the preserved Kaizen receiver. A stored enquiry does not establish that an email notification was delivered. Direct changes to generated `src/formConfig.ts` require reconciliation before reopening; change Client settings and export again to preserve editability.
- Configuring a site origin generates canonical/Open Graph metadata, sitemap.xml and robots.txt. Noindex pages and redirect aliases are omitted from the sitemap. The first page's root alias uses its named route as canonical. Astro integration's sitemap covers builder pages only; existing code-managed sitemap/robots routes produce a conflict for developer reconciliation. Existing host redirect configuration requires applying the included Nginx snippet or equivalent rules; writing files does not activate hosting rules.
- Actual local Nginx checks verify separate client staging/production stores, activation, failure recovery, unpublication and rollback. Unity's companion reconciles the verified live baseline separately from drafts; the server-only CLI does not update that metadata. Local checks do not verify hosted owner/editor/publish permissions or production deployment.

`SITE-SETTINGS.md` in the export lists the chosen services and states that the generated snapshot needs no environment variables or secrets to build. A form receiver's private environment belongs to that separately implemented service. Astro integration keeps service/hosting guides under `.kaizen/handoff/` and redirect snippets under `hosting/`. Settings and receiver URLs are public configuration, not proof of deployment authorization or delivered notifications.

## Hosted project setup and access

Apply the existing builder migrations followed by `202609110001_builder_projects.sql` and deploy `builder-projects` and the updated `builder-publish` functions together. The new function checks the supplied JWT itself; keep its configured `verify_jwt = false` gateway setting. Existing builder function origins must include the hosted editor origin. Configure the public frontend variables `VITE_BUILDER_CLOUD=1`, `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY`; never expose the service-role key in frontend configuration.

The dashboard lists only the signed-in user's projects. Owners can manage existing Supabase user IDs through **Project access**, choose owner/editor roles and grant publication separately. Adding membership sends no invitation email. Removing the final owner is refused. New accounts can create their own isolated projects; project access does not grant access to the original Kaizen workspace. Existing Kaizen editors retain their prior publish permission during migration, with one initial owner assigned deterministically by user ID; review these roles after deployment.

New project files use the private `builder-project-files` bucket. Saved data contains stable project-specific asset references; display/download URLs expire after one hour. Existing signed URLs remain usable until expiry even after membership removal, as is normal for bearer URLs. Display URLs renew after 50 minutes and are checked when returning to a tab or reconnecting. Renewal changes only rendering: unsaved edits, undo history and saved revisions keep their original canonical asset references. A temporary failure keeps still-valid media visible, then suppresses expired URLs and offers **Retry media**. Downloads and exports request fresh Storage access. Account changes immediately clear the old account's presentation and discard pending responses. The API rechecks access for new reads and writes, and clients cannot overwrite original asset bytes used by history. The original Kaizen asset bucket retains its existing behavior.

Run `node tests/builder/verify-hosted-projects.mjs` against the intended test deployment with `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY` supplied privately in the process environment. It creates and cleans up uniquely named test accounts and projects, and checks independent drafts, API/database/storage isolation, immutable media, publication permission and revocation. A passing local database suite does not substitute for this live check.

## On-page editing (September 2026 implementation)

Open the client project, connect the helper to its website folder, and return to **Pages**. **Pages from the website's code** lists the inspected routes. **Edit** opens the original page inside the editor, with Outline, Assets and Sections alongside it. The older existing-page inventory opens the same editor.

On the first preview build, check the displayed command and scripts and click **Build**. Later builds with the same scripts in the same helper connection reuse that consent; a changed command or a new connection asks again. Builds retain the previous snapshot while the updated preview is prepared. Nothing is installed or published by this flow.

Double-click a safely matched text element, or focus it and press Enter, to type on the page. Clicking a link selects its text and address. **Replace image** uses the project asset library; the file proposal includes the copied image and original source edits. Section arrows and drag work only when the rendered group matches the inspected source; the Sections panel remains the fallback. Grey content is managed by code or a CMS, or cannot be matched safely. Imported shared-file changes affect every page using that file. General design changes to unregistered source components remain outside this editor's controls.

Drafts are saved by the helper with a browser recovery copy while a save is pending. **Review my changes** shows the affected files. **Apply changes to the folder** writes the reviewed source patches and rebuilds the preview. Review and apply retain version checks and recovery copies. An image filename contains its checksum, so copying the same image again does not duplicate it.

After apply, **Commit these changes** records only the files belonging to that applied proposal. It checks the current bytes, Git identity, branch and repository state. Existing staged files, a merge/rebase, changed applied files or an unavailable applied proposal stop the commit. A failed Git command leaves the applied files available for review in GitHub Desktop. It never stages the entire repository, amends, pushes or publishes. Push through GitHub Desktop; the website then deploys through its existing process. Configured Kaizen client destinations still use Releases.

Chromium's HTTPS-to-loopback frame needs the browser's Local Network Access permission in addition to helper folder approval. A failed frame offers the window preview and the local editor. The local editor fallback explicitly selects local mode on the loopback development server, even when that server also has hosted settings configured. See [current browser evidence](existing-site-visual-editing-plan.md#browser-support--implementation-log-12-september-2026); the Codex in-app browser connected the real helper and built the page, but left the hosted frame blank. The local fallback rendered and completed a reviewed text apply/rebuild/restore. Hosted on-page input, hosted Firefox and Safari remain unaccepted; those results must not be inferred from the Linux fixtures.
