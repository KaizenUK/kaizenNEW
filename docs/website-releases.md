# Retained website releases

The public deployment workflow now stages a complete build outside the live web root, records checksums and switches one Nginx include. It does not copy a candidate over the live files. The original static HTML, CMS content, generated redirects and build assets are retained for rollback. There is no automatic pruning.

`scripts/kaizen-releases.mjs` provides `stage`, `init`, `activate`, `rollback`, `list` and `verify-live`. It uses Node 22 or later and ordinary filesystem operations. Activation runs `nginx -t` and `nginx -s reload`, using `sudo -n` when the deploy user is not root. [Nginx documents its configuration validation and graceful reload behaviour here](https://nginx.org/en/docs/control.html).

## Builder browser origins

Each service has one server-side allowlist. Supply the helper setting in the environment of the process running `pnpm dev`; set the two function settings through Supabase's function secrets. These are public origin names, not credentials, but they control server access and must not use a `VITE_` prefix.

| Service                  | Setting                     | Default when absent                                                                         |
| ------------------------ | --------------------------- | ------------------------------------------------------------------------------------------- |
| Local helper             | `BUILDER_COMPANION_ORIGINS` | `https://kaizenweb.co.uk`                                                                   |
| Editor/Studio functions  | `ALLOWED_STUDIO_ORIGINS`    | `https://kaizenweb.co.uk,http://localhost:3333` (the existing editor configuration example) |
| Builder contact receiver | `BUILDER_CONTACT_ORIGINS`   | `https://kaizenweb.co.uk,https://www.kaizenweb.co.uk`                                       |

A configured comma-separated list **replaces** the default; an explicitly empty list allows no browser origins. Use complete HTTPS origins, without a path, query, fragment, credentials or wildcard. Plain HTTP is accepted only for `localhost`, `127.0.0.1` or `[::1]`. Root trailing slashes, host casing and standard ports are normalised; duplicates are removed. Invalid entries reject configuration instead of falling back, and errors never echo the entered values.

For example, `BUILDER_COMPANION_ORIGINS=https://builder.example pnpm dev` accepts pairing from that hosted origin after the normal explicit folder approval. It does not grant account access, approve a folder automatically or change loopback/Host checks. `BUILDER_COMPANION_TEST_ORIGIN` remains a test-only supplement that accepts only an exact HTTP loopback origin; a remote origin cannot enter through it.

`PUBLIC_SITE_ORIGIN`, `VITE_PUBLIC_SITE_ORIGIN`, Studio URLs and redirect/cookie settings no longer add allowed origins implicitly. When deploying this change, explicitly include every authorised production, staging and Studio origin in `ALLOWED_STUDIO_ORIGINS`. Those URL settings still select their original redirect destinations; they simply do not grant browser access. Restart the helper or redeploy the affected functions after changing these values. Origin checks complement authentication and project membership; requests without an Origin retain the existing authenticated server-request behaviour.

## Required one-time VPS setup

**Complete this before deploying the updated workflow.** The workflow fails before changing the live files if its release store is absent. The current production host configuration is recorded below; new hosts still need the setup in this section.

1. Choose a dedicated directory outside all public web roots and outside the Git checkout. Use different directories for production and staging, for example `/var/lib/kaizen/production` and `/var/lib/kaizen/staging`. The deployment user must own the directory; Nginx workers need read/traverse access. Do not expose the store itself through a server root or alias. Only the selected `site/` and shared `_astro/` assets are public.
2. From a reviewed checkout containing these scripts, capture the **currently served** static directory as the baseline. It must contain `index.html` and `builder/index.html`. Ensure its `redirects.generated.conf` matches the current generated redirect include; if the live include is stored elsewhere, copy that file into a separate baseline copy first. Leave the existing live directory intact.

   ```bash
   node scripts/kaizen-releases.mjs stage --source /existing/public/web-root --store /var/lib/kaizen/production --id baseline
   node scripts/kaizen-releases.mjs init --store /var/lib/kaizen/production --id baseline
   ```

3. In the intended Nginx server block, replace its existing `root` directive and generated-redirect include with:

   ```nginx
   include /var/lib/kaizen/production/active.conf;
   ```

   Keep the site's TLS, security headers, location routing, error pages and `index index.html` configuration. The managed include supplies `root`, the release's redirects, `location ^~ /_astro/` and the exact release-marker location. Remove duplicate definitions of those locations. Do not leave an old `root` override in the location serving builder pages. Nginx validation and the public response checks must pass before proceeding. The first setup switches to a retained copy of the baseline; it does not delete the old live directory.

   ```bash
   sudo nginx -t
   sudo nginx -s reload
   node scripts/kaizen-releases.mjs verify-live --store /var/lib/kaizen/production --id baseline --origin https://kaizenweb.co.uk
   ```

4. Add `VPS_RELEASES_DIR_PROD` and, if used, `VPS_RELEASES_DIR_STAGE` to the existing GitHub Actions secrets. Keep the existing VPS SSH, application-directory and public-domain settings. The old `VPS_WEB_ROOT_*` and generated-redirect include secrets are no longer used by the public deployment step. Grant the deployment user permission to run the two specific Nginx commands without an interactive password. Do not grant a broad privileged Node command.

Repeat the baseline setup for staging before enabling staging deployment. Existing separate Studio hosting remains optional. It receives the exact Studio files from the retained public release; that separate copy still uses its existing rsync mechanism. The public release, including `/builder/` and its bundled `/studio/`, uses the new activation mechanism.

Manual workflow runs support `preflight_only` to validate access, the release store, Node and Nginx without a build or activation. Staging uses repository variables `KAIZEN_STAGE_APP_DIR`, `KAIZEN_STAGE_RELEASE_STORE` and `KAIZEN_STAGE_DOMAIN`, defaulting to the verified `/srv/kaizen/staging` checkout, `/var/lib/kaizen/staging` store and `stage.kaizenweb.co.uk`. The legacy `VPS_*_STAGE` secrets are not used: their prior checkout path rejected deployment access. Its preflight requires the protected production checkout, store and hostname, and refuses equal, nested or symlink-overlapping paths and equivalent production hostnames. `tests/deploy/preflight.sh` covers those refusals alongside missing configuration, unsupported Node, rejected Nginx configuration and a separate valid destination; both deployment and builder CI run it. A separate staging Studio copy requires the explicit repository variable `KAIZEN_STAGE_STUDIO_ENABLED=true` and reviewed staging Studio settings. The release still includes `/studio/` without that optional copy.

The workflow resolves main/stage once, checks out that branch, records its exact commit and uses the same commit on the VPS. A repository dispatch targeting staging cannot also deploy production because the workflow happens to run on the default branch. Root and Studio dependencies are installed before the complete build. A process-held `flock` serialises use of the VPS checkout through staging and activation.

Each release lives under `releases/<id>/` with:

- `site/`: complete static output, including a public `.well-known/kaizen-release.json` marker containing only release ID, creation time and source commit.
- `redirects.conf`: the exact generated redirect rules, outside the served site.
- `release.json`: the file list, SHA-256 checksums, redirect checksum and expected public responses, outside the served site.

Staging rejects symlinks, file traversal, missing entry pages and local workspace/server files. Apache/PHP `.htaccess` and `.user.ini` files stay in the source output and are excluded from the Nginx public artifact. Activation rechecks every retained file, verifies the currently served baseline, installs immutable hashed build assets, writes `active.conf` atomically, validates Nginx and reloads it. New native manifests use version 3 and verify the exact marker and every public file, including existing native pages, styles, scripts, images and Studio assets. Client manifests retain version 2 with full-file checks; retained native version 1 releases keep their original page checks for rollback compatibility. Verification bypasses normal caches, closes connections and allows bounded observation of graceful reloads. A marker alone is insufficient to report success. New artifacts record `responseIdentity: release-id-v1` in the manifest and hashed marker. Their Nginx configuration emits `X-Kaizen-Release` on each response; every file and redirect check must have the expected ID as well as the expected bytes/status. This prevents responses from different graceful-reload workers from being combined into a successful verification. The complete baseline is observed with the same bounded retry before activation mutates anything. Older artifacts and the exact earlier configuration format remain compatible; retained files are not rewritten.

Shared `_astro/` files remain available to visitors with an earlier page open. Existing names must have identical bytes; a content collision fails activation. Assets are added through complete temporary copies before selection. Retained release files are not modified when switching or rolling back.

Transactions under `transactions/` record checking, activating, verifying and live states. A failed candidate restores the previous include, validates and reloads Nginx, and verifies the previous public responses. Only then does it record `rolled_back`. If the include was changed by an administrator, or recovery cannot be verified, it records `recovery_required` and reports the exact transaction; it does not claim the old site was restored. A candidate can be briefly served during its final HTTP verification; failure recovery returns serving to the prior release.

The generated redirect rules support exact internal paths with letters, numbers, slashes, dots, hyphens and underscores, with 301/302 responses. Invalid paths, configuration injection, duplicate sources and cycles fail the build. External redirects, query strings and regex patterns require deliberate additional support rather than raw Nginx interpolation.

## Hosted repository transport

The L1 client calls `POST /editor-api/builder-repository` on the builder's own origin. Each JSON request preserves its existing `repository-*` action fields and adds the selected `projectId`. The bearer token comes from the current Supabase session, is sent only to this fixed first-party endpoint, and is never forwarded across redirects. Neither the query string nor a local folder preference supplies an endpoint. Explicit developer tabs use `helper=local` and the existing approved companion window instead; transport selection is fixed for the document's lifetime.

The initial `repository-connect` action must verify the session, current project membership and configured working copy before returning `{ projectId, root, expiresAt }`. `root` identifies that project's folder and must stay the same within the connection; `expiresAt` is an absolute Unix timestamp in milliseconds. The client bounds the lease by the JWT expiry and rejects a mismatched project, expired lease or changed folder. Other actions return the existing helper result shape, or a non-2xx JSON `{ error }`. Every call still needs a server-side membership/path/plan check; browser checks are not an authorization boundary.

401/403, unavailable-service responses and connection loss end the client's connection while preserving recovery. Conflicts keep their original message. A timeout or account change can leave an already accepted write's outcome unknown; the client does not resend it automatically. Token refresh and return from the browser's page cache establish a fresh connection. Failed requests use the safe operator diagnostics path.

The endpoint is served by the loopback hosted-helper service. Add its exact proxy route ahead of the existing `/editor-api/` Supabase proxy when rolling out L1, together with the preview route below. Build jobs, protected HTTPS previews and explicit Save to website are implemented. Kaizen provisioning and full operations follow in L1-T6–T7; do not deploy the intermediate client default by itself.

Hosted preview URLs must be on the builder's origin under `/editor-preview/<project>/…`. The client refuses another project, outside origin, credentials or escaped path separators and uses an opaque `allow-scripts` sandbox, including previews opened in a window. The protected delivery below supports actual Astro/React snapshots in that sandbox. Earlier transport-only fixtures retain their HTTP adapter; the dedicated `hosted-preview.spec.ts` scenario exercises the actual hosted service through a real TLS proxy.

### Hosted working-copy service

`pnpm builder:hosted-helper` starts `scripts/builder-hosted-helper.ts` on Linux, listening only on `127.0.0.1` (default port 4334). Run it as a dedicated service account with a private home and no unrelated Git configuration or credentials. The service currently handles connection, repository/source inspection, account-specific source drafts, source/export review and apply, Git status, explicit fetch, reviewed build jobs with status/cancellation, protected general/selection/canvas previews, private folder-backup review/download and configured Save to website. The separate `repository-save` action commits and pushes after the editor clicks **Save to website**. Legacy `repository-commit` and opening/restoring builder archives remain unavailable through this service; they never fall through to the local helper. Kaizen provisioning and operations are still required for rollout.

Set these in the service environment, without `VITE_` prefixes:

| Setting                                | Purpose                                                                                                                                                                                                                    |
| -------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `BUILDER_HOSTED_PROJECTS_FILE`         | Absolute path to operator-owned repository configuration; use [the example](hosted-repositories.example.json).                                                                                                             |
| `BUILDER_HOSTED_WORK_DIRECTORY`        | Dedicated private directory for working copies, drafts and locks, outside the web root and developer checkouts.                                                                                                            |
| `BUILDER_HOSTED_CREDENTIALS_DIRECTORY` | Separate private directory for per-project SSH files; must not overlap the work directory.                                                                                                                                 |
| `BUILDER_HOSTED_SUPABASE_URL`          | HTTPS Supabase project origin.                                                                                                                                                                                             |
| `BUILDER_HOSTED_SUPABASE_ANON_KEY`     | API key used with the caller's verified access token. A service-role key is not required.                                                                                                                                  |
| `BUILDER_HOSTED_PORT`                  | Optional loopback port.                                                                                                                                                                                                    |
| `BUILDER_HOSTED_EDITOR_ORIGIN`         | Required canonical HTTPS editor origin, with no trailing slash or path. It must also be in `ALLOWED_STUDIO_ORIGINS`.                                                                                                       |
| `BUILDER_HOSTED_GITHUB_READ_TOKEN`     | Optional server-only GitHub token with Actions read access to the configured private repository, used only to observe staging and production deployment runs. Never put it in client configuration or a build environment. |
| `ALLOWED_STUDIO_ORIGINS`               | Explicit allowed editor origins, with the parser/defaults described above.                                                                                                                                                 |

The repository file has `version: 1` and a `projects` array of `{ projectId, repositoryUrl, branch, saveToWebsite?, publishToWebsite? }`, or explicit empty setup admissions described below. It supports explicit `git@hostname:owner/repository.git` SSH addresses and ordinary branch names. Local/file/HTTP URLs, URL credentials, executable protocol extensions and Git-option inputs are refused. Owners can change the repository and branch through the dedicated settings actions; ordinary editing, save and publication requests cannot choose them. Credential paths and deployment approvals remain operator-controlled.

For each configured ID, provision `<credentials>/<projectId>/deploy-key` and `<credentials>/<projectId>/known_hosts` under the service account. Directories must be mode 0700 and these files mode 0600, owned by that account, without symlinks or hard-linked credential files. Put only the public half of that project's deploy key into the Git host. Pin the Git host's independently verified SSH host key in `known_hosts`; a scan alone does not verify its identity. Clone/fetch/push uses this one identity, strict host checking, no SSH agent, no interactive prompts, no global Git/SSH configuration and no inherited service secrets. Raw Git/SSH errors are not returned to the browser.

Each project receives `<work>/projects/<projectId>/checkout`. The first authorized action clones only the configured branch into a temporary folder and moves the completed clone into place. A private repository marker preserves its project ID, repository address and branch. Later calls verify the real folder, `.git` directory, origin and branch, and reject linked/shared Git stores, Git URL rewrites/includes or a changed identity. They do not reset, replace or silently reclone an existing working copy. Repository/branch changes use the explicit owner setup transition below, preserving the old folder and its drafts. Deployment display/tracking settings do not change that identity. `repository-fetch` updates remote-tracking refs only. It does not pull, merge, push or overwrite pending source edits.

Every request first verifies its bearer token with Supabase Auth. It calls the existing `builder_project_access` database function as that user with `capability: "edit"`, including a second check after waiting for the project lock. Archived projects and revoked/non-members are refused before repository work begins. The old editor cookie by itself grants no repository access. There is no membership cache. A request already authorized and executing can finish after membership is revoked; later calls must pass a fresh check.

One operation per project runs at a time, with a bounded in-process queue and an exclusive file lock shared by service processes. Different projects can proceed independently. A stopped process's lock is deliberately not stolen automatically: establish that its operation has stopped, preserve its working copy, and remove only that specific lock before retrying. Full restart/health/rotation/disk-limit procedures remain L1-T7. Review IDs are limited to their verified account/project, bounded and expiring, and consumed before an apply attempt. Account drafts live outside the checkout in that project's private data; another member cannot use their review IDs or backup downloads. Concurrent source changes retain the existing conflict/recovery protections.

The service bounds HTTP concurrency, project queues, upload size and upload/auth/Git waits. Repository POSTs reject unsupported content encodings, wrong origins, cookie-only calls, unknown actions and cross-folder/nested-root inputs. Preview reads and session revocation use the separate cookie rules below. Existing repository modules retain source path and symlink checks. Client-visible failures use the L0 safe reporting path; server startup errors contain a fixed configuration message. Build isolation for client code remains the L5-T4 decision. Only operator-approved Kaizen code belongs in this beta service.

### Save to website

Enable saving for a project with `saveToWebsite: { "environment": "staging", "url": "https://stage.example", "workflow": "deploy.yml" }` in the private repository configuration. The URL must be an exact HTTPS origin without a trailing slash, credentials or path. `workflow` is optional and must name a `.yml` or `.yaml` workflow file in the configured GitHub repository. Before enabling this capability, the operator must verify that pushing the configured branch deploys only staging, that the destination URL identifies that staging site, and that the named workflow actually performs its deployment. The service cannot infer those properties from a branch name. Give the project's deploy key write access to that repository and retain branch protections compatible with the intended staging push. Projects without this configuration do not advertise the Save button; the save API returns a setup error.

After **Review my changes → Apply changes to the folder**, the editor offers **Save to website**, a change summary and a separate **Save details** disclosure. Source and generated-export applies use the same existing commit module. Only the applied files enter the commit, with the name (`full_name`, then `name`) and email returned by verified Supabase Auth. Missing/invalid account details require correction before saving; request-supplied authorship is ignored. Unrelated staged files, unfinished merges/rebases, changed applied bytes or a moved local/remote branch refuse the save with an explanation. Unstaged unrelated work stays outside the commit. A preview build does not push. The page canvas disables Save during a build, and the server independently blocks saves from any screen while the build lock is held.

Saving holds the project lock, checks current remote HEAD against the base recorded at apply, creates the commit, and rechecks sign-in and membership before pushing. The push addresses the configured SSH repository and one exact branch ref. It uses an explicit `--force-with-lease=<ref>:<base>` as a compare-and-swap **only after independently proving that the actual commit object has exactly one parent equal to that base and is still local HEAD**. Replacement refs and ancestry grafts cannot disguise this proof. This combination permits one new commit without replacing remote history and rejects both remote advances and rewinds between checking and pushing. The lease never depends on a mutable tracking ref. Git's [explicit expected-value lease semantics](https://git-scm.com/docs/git-push) define the remote check. Hooks, signing, automatic tag pushes and submodule pushes are disabled for these service commands, which receive the existing restricted Git/SSH environment.

An interrupted or rejected push keeps the commit and files. **Check saved state** only reads the remote; it can resolve a lost acknowledgement when the exact commit is present and never pushes. **Retry saving to website** explicitly retries that same commit. Reopening the page restores this account's applied/saved receipt while the service remains running. An unsent commit blocks another apply, preserving its retry path; a later apply supersedes an earlier uncommitted apply as in the existing local workflow. Completed receipt history is bounded. Receipts are currently in memory: after a restart, the operator must preserve and inspect local HEAD, remote HEAD, staged files and pending drafts before reconciliation. Do not replay a lost save automatically. Durable restart recovery is L1-T7.

A confirmed push shows **Open staging** and observes the optional GitHub Actions workflow by the exact repository, workflow, commit, branch and `push` event. It reports waiting, deploying, success, failure or unavailable status, with a validated link to the run. Queries follow GitHub's [workflow-run API](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28#list-workflow-runs-for-a-workflow); responses are cached briefly and private repositories need the read token above. Missing tracking, API failures or a failed deployment do not turn a successful Git save into a failed push. Workflow success is evidence of that workflow's result, not proof that a browser is serving the intended revision. Open staging and check the page before **Publish** through Releases. Save never requests publication.

### Publish the staged website

Native-source publication is a separate, explicit action in **Releases → Publish website changes**. Enable it only after verifying both destinations and their deployment workflows. Add `publishToWebsite: { "environment": "production", "branch": "main", "url": "https://www.example", "workflow": "deploy.yml" }` alongside the approved staging configuration. The production branch and exact HTTPS origin must differ from staging; the same SSH repository and private deploy key are used. The operator must verify that a push to that production branch deploys the intended live website, respects its branch protections, and verifies served output. Do not enable this approval on the live Kaizen helper until staging and production are wired and checked. The example is a configuration shape, not evidence that either destination is deployed.

1. Save changes to staging, open staging and check the page.
2. Choose **Review staged website** in Releases. This freezes the saved staging commit, the current production branch base, the changed-file list and staging release identity. Technical details remain in **Publication details**.
3. Choose **Publish reviewed changes** to advance the approved production branch to that exact staging commit. This creates no extra commit and leaves the website folder on its staging branch. The existing production workflow then builds and verifies that source revision.

The three `repository-publish-review`, `repository-publish` and `repository-publish-status` actions require current edit **and publish** permission before disk access and again after the project lock. Ownership alone does not grant publication. Immediately before starting the push, the helper re-verifies Auth and publish permission after resolving Git history and credentials. Reviews belong to one publisher and project, expire within the current session or 15 minutes, and cannot be selected through request-supplied commits, branches or destinations.

Review and publication refuse unsaved/untracked Git work, unfinished Git operations, active/queued builds, outstanding unsent saves, changed staging or production branches and unavailable staging deployment identity. The helper fetches production objects without changing the checkout and walks the actual commit parent headers to establish that production's reviewed base is an ancestor of staging. Replacement refs and ancestry grafts cannot disguise divergent history. The walk is bounded at 512 commits, with at most 500 changed paths in a review; larger histories need operator reconciliation. An explicit expected-value lease on the production ref rejects both advances and rewinds between checking and pushing. It only permits the already-proven fast-forward from the frozen production base.

Before review and again before publishing, the helper reads `/.well-known/kaizen-release.json` from the approved staging HTTPS origin. The second read must match both the commit and release ID reviewed. These reads carry no editor or GitHub credentials, reject redirects and bound the response size. **A public release marker identifies the reported revision; it does not attest every served byte.** The configured deploy workflow must retain its served-output verification, and Sean's real-page check remains part of acceptance. The Releases card separately reports the Git push, the exact production workflow's status and the live website's reported revision. It never labels a successful push or matching marker as complete release verification.

A rejected push keeps the reviewed staging revision. **Check publication state** is read-only: it resolves an unknown acknowledgement when the exact commit reached production, allows an explicit retry when production still has the reviewed base, and refuses further publication when a different production revision makes the outcome ambiguous. It never pushes again automatically. An unresolved outcome blocks repository retargeting and new publication reviews. Receipts remain in memory until L1-T7: after a helper restart, preserve and inspect staging/local/production heads and deployment history before reconciliation; never replay a lost publication. Builder-owned content continues through its existing release queue separately.

### Owner repository setup

In hosted projects, owners have a **Website repository** card in Settings. Editors do not see it. The four `repository-settings-read`, `repository-settings-save`, `repository-settings-key` and `repository-settings-connect` actions require both current edit access (including an unarchived project) and current ownership, before accessing the filesystem and again after acquiring the project lock. These explicit setup actions work before the website folder connects; other repository actions still require a connection. Account changes discard the previous account's setup screen and pending responses.

The operator first admits the project in `BUILDER_HOSTED_PROJECTS_FILE`. A complete repository entry supplies its initial SSH address, branch and optional staging approval. `{ "projectId": "<existing-project-id>", "setup": true }` admits an empty setup; it does not create a project, grant membership or enable staging. Before an owner connects, create the project's private credentials directory and a mode-0600 `known_hosts` file with independently verified Git-host keys. Directories are mode 0700; files and directories belong to the helper account. Only those pinned hosts are accepted. See [GitHub's published SSH fingerprints and host keys](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints). Do not trust an unverified key scan.

1. Enter the repository's SSH address and intended website branch, then **Save repository settings**. Only these two values are accepted; private keys, local paths and deployment approval cannot be supplied by the browser.
2. Choose **Create deploy key**. The helper creates an Ed25519 key on the server. Copy the public half and add it to that repository's deploy keys. **Save to website** requires the Git host's write-access option; [GitHub documents deploy-key setup here](https://docs.github.com/en/authentication/connecting-to-github-with-ssh/managing-deploy-keys).
3. The public key appears only in the creation response and remains on this screen until dismissed, refreshed or left. Later reads return its fingerprint, never either key half. **Copy public key** and **I've added this key** support that one-time handoff. An unconnected setup key can be explicitly replaced if its public half was lost; remove the obsolete key from the Git host after the replacement works. Connected-key rotation requires the operator.
4. Choose **Check website folder**. The helper uses the key to clone the configured branch and verifies remote access; checking an existing folder also rechecks the remote. A rejected key leaves the setup available to correct. Dependencies still require operator provisioning before preview builds.

Settings carry a version so an outdated tab cannot replace a newer setup. Changing repository or branch refuses pending Git work, a different remote HEAD, active/queued builds, unsaved apply/commit receipts and an unknown production push outcome. A successful change invalidates old plans, previews and completed save/publication receipts, retains the old checkout and its identity record under `<work>/projects/<project>/previous-setups/`, and requires a fresh connection. A branch change keeps the repository's key. A repository-address change requires a new key; the old private key is retained only under `<credentials>/<project>/previous-keys/`, outside the working-copy area. Retention limits and connected-key rotation procedures belong to the operations task.

### Hosted build jobs

`repository-build-review` returns the existing command/scripts and source fingerprint. `repository-build-start` accepts that account's unexpired review once and returns a project/account-bound UUID with `status: "queued"` and `queuedAt`. Poll `repository-build-status` using that ID for queue position, `building` with `startedAt`, and terminal `succeeded`, `failed` or `cancelled` with `finishedAt`. The log contains at most the most recent 100,000 characters and is available during execution. The editor polls active jobs, retains their ID for reopening, and offers **Cancel build**. Reopening a known failed or cancelled build preserves its result; **Try building again** or **Build again** explicitly starts a fresh command review.

The queue follows the publication jobs' project scope, queued/building phases, exclusive claim, bounded log and explicit failure conventions. It reuses `RepositoryRunner` for command/source validation, process execution, recovery and snapshots; these preview-only jobs do not enter `builder_client_jobs`, activate a destination or publish. One build runs per project, with two projects building concurrently. Up to eight queued/running jobs per project and 64 across the service are accepted; older completed results are pruned as more jobs are added, bounding retained history per project. Source fingerprints and the 15-minute command review are checked when execution starts, as are the captured caller's sign-in and current membership. A token that expires while queued requires a fresh review. The captured token stays only in memory until that start check or cancellation; it is never written into a job or log response. A running authorized build can finish after access is revoked, but later status/cancel requests still require current access.

A separate `<work>/locks/<projectId>.build.lock` is claimed while holding the normal project lock, then retained through execution, process cancellation and output recovery. This blocks apply, fetch and native backup capture while keeping source inspection, draft saving, log/status polling and cancellation available. A cancelled queued job never runs. A running cancellation reports `cancelling: true` until the runner has finished; the terminal result follows recovery and build-lock release. The next queued job then starts. Changed source invalidates a queued review rather than building unreviewed code. Existing or replaced lock files fail closed and require operator inspection.

Build scripts receive a restricted environment with a private per-project `build-home` and `build-temp`, the service's executable search path, fixed locale and disabled global Git/npm configuration. They do not inherit the service's Supabase credentials or SSH agent. Dependencies must already be provisioned by the operator; accepting a build does not install packages. The existing runner enforces its five-minute build limit and preserves previous `dist/` output under `.kaizen/build-recovery/`, restoring it after failure or cancellation. This environment restriction does **not** isolate scripts from other files owned by the service account. It is suitable only for the trusted Kaizen beta; container/separate-host isolation for clients remains the L5-T4 decision.

Queue state and logs are currently in memory. A graceful service close cancels queued/running jobs, waits for recovery and closes snapshots; jobs are never automatically replayed. A process crash can leave a build lock and recovery directories that must be inspected before the folder is changed. Durable restart evidence, disk retention and the service manager's process cleanup are L1-T7. Successful status responses expose the protected HTTPS preview URL while the runner's snapshot remains available; closed or expired previews lose that URL. The runner's loopback URL is never returned to a hosted editor.

### Protected HTTPS previews

The service exposes `GET`/`HEAD /editor-preview/<project>/<build>/<view>/…` on loopback for TLS termination by Apache. Every response comes from the runner's frozen build map; request paths never become filesystem reads. Source editing first reuses the runner's source fingerprint and route checks. Rewriting is confined to served snapshot bytes; source and `dist/` stay authoritative. General website previews, the embedded canvas and the source-selection fallback share this delivery path.

Successful canonical-origin repository calls establish or renew `__Host-kaizen_builder_preview`: a random server-side session ID with `Path=/; Secure; HttpOnly; SameSite=Lax`, no Domain attribute and no token in the cookie. Its lease is bounded by 15 minutes and the verified JWT expiry. The unsigned legacy Studio cookie `kaizen_studio_auth=1` grants no access here. Sessions, public views and frame grants bind the verified account to its project and build. Each document, bootstrap and asset request checks Supabase Auth and current edit membership, fails closed during an Auth outage, and checks that the build is still available. There is no membership cache. Sign-out/account changes send an origin-checked DELETE to the existing repository endpoint to invalidate that session and its frame credentials. If the service is unreachable, the session expires without renewal. Already delivered bytes and an already authorized read cannot be recalled.

The iframe remains opaque (`sandbox="allow-scripts"` plus the same CSP sandbox), so page scripts cannot read the parent's document, editor storage or cookies. Authenticated HTML contains a private content namespace distinct from the shareable document URL and a one-use bootstrap grant. Its parser-blocking script installs a `Secure; HttpOnly; SameSite=None; Partitioned` frame cookie scoped to that namespace before the original assets are discovered. The bootstrap URL is a short-lived credential revealed only inside authenticated HTML; it expires after 30 seconds and cannot be reused. Frame credentials expire with the session or snapshot. The public URL alone cannot obtain bootstrap/asset access, including with `Origin: null` and an ambient editor cookie. No Supabase access token is placed in a URL, script or built file. Internal links in the general preview ask the trusted wrapper to load the next document: it checks the sending frame, opaque origin, view nonce and route within the same project/build/view. This keeps navigation initiated by the editor, where the document cookie is available. Direct script-driven navigation and client routers that require same-origin storage/history may be unavailable in this restricted preview.

Local scripts, module preloads and inline imports opt into credentials, and authenticated frame responses allow credentialed CORS only for the opaque `null` origin. The private namespace prevents a different opaque frame that knows only the shared URL from reading assets with an ambient cookie. This retains the [HTML script credentials rules](https://html.spec.whatwg.org/multipage/scripting.html#attr-script-crossorigin) without granting same-origin script access. Local CSS fonts are embedded from the same frozen map because [CSS font fetches use anonymous CORS](https://www.w3.org/TR/css-fonts-4/#font-fetching-requirements); limits are 5 MiB per font and 8 MiB of embedded bytes per stylesheet. Larger fonts retain their URL and may be unavailable in this restricted preview. Relative assets resolve against a trusted private base; root asset URLs and JavaScript URL literals are rebased only in the response.

CSP permits scripts only from the private snapshot plus existing inline scripts. It disables network calls (`connect-src 'none'`), forms, subframes and objects, limits framing to the canonical editor, and allows only the private base URL. HTTPS images, styles and fonts remain permitted for existing site presentation; remote scripts, application API calls and embedded third-party frames do not run. Preview responses use `private, no-store`, `nosniff`, `no-referrer` and restrictive permissions. The service bounds concurrent preview reads at 32, sessions at 512, views at 1024 and bootstrap/frame grants at 2048 each, with per-build/per-document eviction. Restart clears all grants; reconnect and build again. Arbitrary client build isolation and the wider browser matrix remain L5, while service lifecycle/disk retention remain L1-T7.

For Apache/DirectAdmin, place the following in the canonical editor's **HTTPS virtual-host custom configuration**, ahead of the generic `/editor-api/` and `/` proxy rules. Preserve it in the existing domain-specific DirectAdmin custom template; do not copy it into unrelated subdomain branches. Apache processes matching proxy rules in order, as documented in [ProxyPass](https://httpd.apache.org/docs/2.4/mod/mod_proxy.html#proxypass). The repository rule uses an explicit capture and backreference: without a backreference, [ProxyPassMatch](https://httpd.apache.org/docs/2.4/mod/mod_proxy.html#proxypassmatch) appends the original path to its target, duplicating a destination that already contains that path.

```apache
ProxyRequests Off
ProxyPassMatch "^(/editor-api/builder-repository)$" "http://127.0.0.1:4334$1" connectiontimeout=5 timeout=120 retry=0
ProxyPassReverse "/editor-api/builder-repository" "http://127.0.0.1:4334/editor-api/builder-repository"
ProxyPass "/editor-preview/" "http://127.0.0.1:4334/editor-preview/" connectiontimeout=5 timeout=120 retry=0
ProxyPassReverse "/editor-preview/" "http://127.0.0.1:4334/editor-preview/"
<IfModule mod_cache.c>
  CacheDisable /editor-preview/
  CacheDisable /editor-api/builder-repository
</IfModule>
```

Keep HTTP-to-HTTPS redirection and TLS certificates on Apache. Forward Authorization, Origin and Cookie and preserve Set-Cookie attributes, including Partitioned; do not widen cookie Domain/Path or rewrite the asset namespace. The preview service owns authentication and its per-response CSP. Exclude these routes from generic login redirects, static fallbacks, caching and any global CSP/header rule that would replace or append a conflicting policy. Do not authorize them by the Studio flag or add a blanket null-origin CORS grant. Keep snapshot URLs, cookie values, bearer tokens and bootstrap grants out of diagnostics; restrict proxy access logs and redact preview paths before sharing them.

Before rollout, validate the generated Apache configuration with its installed config-test command, reload only after it passes, and inspect the actual HTTPS response headers. ## Builder error visibility

The default error sink is `public.builder_client_errors` in the existing Supabase project. This follows L0-T4 without adding another service. A hosted error service is an optional later alternative if Sean wants its search/alerting features; keep the same safe fields and access/retention boundary if changing the sink. No third-party error service is configured.

Apply `202609120002_builder_client_errors.sql` and `202609120003_builder_error_retention.sql` after the project-capabilities migration, then deploy the updated `builder-projects` function and frontend together. Migration 003 requires `pg_cron` and fails if the hourly cleanup cannot be scheduled. Supabase provides the scheduler; self-hosted Postgres must install it first. The syntax follows [Supabase's Cron installation](https://supabase.com/docs/guides/cron/install) and [job quickstart](https://supabase.com/docs/guides/cron/quickstart). Neither migration contains credentials.

The function accepts authenticated `record-error` actions, takes the account ID from the verified token and rechecks current membership and archived state in the recording transaction. A project lock serializes recording with membership changes. Each record contains project/user IDs, a server receipt time, fixed error category/source, known screen, optional page ID/route hash, browser family/major version/platform, and helper mode/state. No raw message, stack, URL, source path, build log, title or arbitrary JSON is stored. There is no diagnostic email or Slack integration.

Only database operators (SQL editor or a server-side service-role client) can read these records. Builder owners and editors cannot select, insert, update or delete them, impersonate an actor through the RPC, or run retention cleanup. Service-role recording must use the guarded RPC; it has no direct table write grant. The client uses explicit event-time authentication and drops pending sends on account changes. No extra secret belongs in the frontend.

Inspect the most recent records for one project using a bound project parameter in an operator SQL client:

```sql
select created_at, project_id, user_id, category, source, screen,
       page_id, route_hash, browser_family, browser_version, platform,
       helper_mode, helper_status
from public.builder_client_errors
where project_id = $1 and created_at >= now() - interval '14 days'
order by created_at desc, id desc
limit 100;
```

The route hash can be matched against a user's copied report. It does not recover the route or error text. Membership permits recording even without publish permission. Revoked members and archived projects are refused. Writes are capped at 20 per account/project per hour and 2,000 per project per day, checked against server receipt times under the project lock. Dropped duplicates/rate-limited events are not counted elsewhere. The browser also limits attempts, deduplicates a repeated category/source/page for one minute, bounds concurrent sends and abandons a slow request. This is troubleshooting evidence, not complete analytics or an availability monitor.

`builder-client-error-retention` runs hourly and physically removes records older than 14 days, including projects with no recent activity. With the job operating, deletion occurs at its next hourly run (up to 14 days plus one hour after receipt). Removing an account or project also deletes its records through foreign keys. This policy covers the live error table; database backups follow the separate backup-retention policy.

Before enabling beta recording, and after database maintenance, verify the job is active and inspect its latest execution in Supabase Cron. Check the actual deployment with:

```sql
select jobid, jobname, schedule, active, command
from cron.job where jobname = 'builder-client-error-retention';

select status, start_time, end_time, return_message
from cron.job_run_details
where jobid = (select jobid from cron.job where jobname = 'builder-client-error-retention')
order by start_time desc limit 5;

select count(*) as overdue
from public.builder_client_errors
where created_at < now() - interval '14 days 1 hour';
```

An inactive/failed job or overdue records require operator action. Correct the job or database issue, run `select public.builder_prune_client_errors();`, then verify the next scheduled run succeeds and `overdue` is zero. Do not claim retention is active based on applying the table migration alone. The worker progresses through queued, building, activating and verifying. **Builder → Releases** polls status while visible, shows the currently verified release, exposes actionable recorded errors and lets an editor retry an unclaimed dispatch. ## Builder redirects

Builder → Redirects provides a separate saved draft, a review of added/changed/removed rules and explicit publication. Both forms of a directory URL (with or without a trailing slash) receive the chosen 301/302 response, preserving query parameters. Temporary 302 is the default because browser caches can retain a permanent 301 after it is changed. History restoration changes the draft only. There is a 200-rule limit; paths are internal, at most 200 characters and use letters, digits, slashes, dots, underscores and hyphens. External URLs, query-specific rules and regular expressions are unsupported.

Install `202609100010_builder_routes.sql` after migrations 001–009, with no pending release, alongside the updated publishing function, generator and worker. Do not reapply an earlier backup migration over the wrapper functions added by 010. Anonymous access exposes only published rules; draft editing and backup access require editor membership. Queued releases freeze redirect rules, ordinary page/site/code releases retain the published set, and verified rollback restores the retained release's rules while preserving newer drafts. A missing redirect field in an older retained snapshot means no builder redirects.

A redirect cannot replace a current builder page or protected existing Astro/editor route. Publish a moved page's new URL first, then publish a redirect from the old URL. Published and pending sources are reserved against page edits. Build-time validation checks conflicts and cycles across builder, Sanity and fixed site redirects and verifies that every builder destination chain ends at an emitted public path. A missing destination fails the build and preserves the previous live site. Removing a page that is still a redirect destination therefore requires updating or removing the redirect first.

The generated `redirects.generated.json` records status, destination and query-preservation checks. Staging stores those checks in the private release manifest and excludes both generated redirect files from the served site. Verification requests both URL aliases with query parameters, checks the exact Location and status without following redirects, and includes these responses in publication evidence. Failure triggers the same retained-release recovery as a bad page response. Legacy artifacts without this metadata retain their previous page checks.
