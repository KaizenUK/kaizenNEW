# Builder signup and the first website

The hosted sign-in screen offers **Create an account** and **Confirm your email**. Signup asks for a name, email and a password of at least 12 characters, with password confirmation. It uses the existing Supabase Auth client. A neutral response tells the person to check their email or sign in to an existing account; it does not reveal whether an address was already registered. Failed requests explain that an email might still have been sent. Confirmation resends use the same neutral wording and retain the provider's request limits.

Confirmation returns to the configured origin's exact `/builder/` route. Arbitrary return URLs, existing project parameters and authentication fragments are not copied into the email redirect. The normal invitation and password-recovery flows remain available. Signing up does not start a paid subscription or record legal acceptance.

After email confirmation, the existing legal gate requests explicit acceptance of the current Terms and acknowledgement of the Privacy Policy. The first-project gate then calls the existing `builder-projects` function's `bootstrap` action. The function verifies the session and supplies the actor itself; browser-supplied account IDs, confirmation timestamps and acceptance claims do not establish authority.

The database checks the active Auth account, confirmed email and current acceptance record again. One transaction creates **My website**, its owner membership with publication permission, an empty workspace and the durable account initialization record. The website has no publication destination and cannot select Kaizen's destination implicitly. A per-account transaction lock serializes simultaneous requests. A failed transaction leaves no partial project; a lost response is recovered by retrying the same action.

Existing accounts are marked initialized during migration. A membership trigger also remembers new invitations. Removing membership, archiving or deleting a website does not erase the initialization or create a replacement website at next sign-in. Previously invited users keep their existing accessible projects. Accounts with no remaining projects use the existing Projects workflow; they are not silently assigned access to Kaizen.

Opening a newly created project changes the document URL before the workspace mounts, disposing the previous document's editor/storage state. Valid explicit project links retain their normal access checks. The gate checks the signed-in account before and after its request and discards late results after an account change, sign-out or unmount. A failed read keeps the workspace unmounted and offers Retry, Reload and Sign out.

## Deployment

This is L6-T1 implementation; production remains on the verified L5 release until the coordinated L6 milestone rollout. Apply `202609150001_builder_signup.sql` before deploying the matching `builder-projects` function and frontend. The new `builder_account_initializations` table has RLS and no direct browser or service-role privileges; only the narrowly granted bootstrap function can initialize an account.

The provider's Auth configuration must enable email signup, require email confirmation, retain the 12-character password minimum and allow the exact production Builder confirmation URL. Configure delivery through a suitable SMTP service and verify its sender/domain configuration before inviting public signup. The configured staging origin needs its own exact allowed URL if staging signup is supported. Do not replace existing invitation/recovery allowlist entries without preserving those flows. Follow Supabase's official [signup API](https://supabase.com/docs/reference/javascript/auth-signup), [confirmation resend API](https://supabase.com/docs/reference/javascript/auth-resend), [redirect configuration](https://supabase.com/docs/guides/auth/redirect-urls) and [SMTP setup](https://supabase.com/docs/guides/auth/auth-smtp).

Read-only provider inspection on 15 September found signup disabled, email confirmation required, email Auth enabled and a 12-character minimum. The site URL is the production Builder route; existing allowlist entries cover the production and www Builder paths. No SMTP host, user or sender is configured. No provider setting or real account/email was changed for this task. Email delivery setup belongs to the final L6 rollout/setup work, not to an invented successful delivery claim.

## Verification

`signup-database.spec.ts` executes the migrations in PGlite and covers first creation, retries, retained drafts, current acceptance, unconfirmed/deleted/missing accounts, invitation and existing-account history, archival/deletion, atomic rollback and privilege denials. The complete table access matrix includes the new private table.

`tests/ops/test_signup_concurrency.py` uses a private native PostgreSQL cluster. It holds the initialization lock until eight independent connections are observed waiting for that exact lock, releases them, and requires one creation, one project/workspace/initialization and the same returned project ID for all eight. It also verifies deletion does not recreate the project. This supplies actual concurrency evidence separately from PGlite's serialized requests; the existing operations CI job discovers it automatically.

`tests/functions/builder-signup.test.ts` imports the real Edge entry point and pinned SDK with only the provider HTTP boundary replaced. It verifies the actor comes from Auth, the service-only RPC is used, hostile origins and invalid sessions stop before initialization, and confirmation/legal/provider failures preserve safe responses. The client tests cover validation, duplicate requests, neutral existing-account outcomes, stale account results, sign-out, malformed responses and project routing.

`tests/builder/signup.spec.ts` uses the real browser SDK and UI with a fake provider and actual database functions. It exercises signup, an actual loopback confirmation redirect, explicit legal acceptance, a lost bootstrap response, retry, document navigation, reload and confirmation resend failures. Chromium, Firefox and WebKit run it alongside account, invitation and legal regression journeys. All data, tokens and email addresses in these checks are synthetic; no live account, personal workspace or real email is a test fixture.
